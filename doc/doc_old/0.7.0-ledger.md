## 0.7.0-rc.2: the fidelity gate, and the 48 bytes

CI 319 refused the rc.2 cut on `density.resident_bytes_per_agent`: 92,210
against a baseline of 91,821. The trace, because every hypothesis on the
way was wrong and the record should say so:

| measurement | resident B / agent |
|---|---|
| committed baseline, C swarm on build13 (captured 2026-09-06) | 91,821 |
| C swarm on 0.15.1, stock | 92,162 |
| C swarm on 0.15.1, workers opened `DV_FLAG_TEXT_ONLY` | 92,210 |
| DRT on 0.15.1 | 92,210 |
| C swarm on build14, workers text-only | 91,869 |
| DRT on build14, current code | 91,869 |

- **DRT has no port drift.** In DRT's configuration the C swarm matches
  it to the byte on both cores. The C bench cannot set the text-only flag
  (`dvs_allow_unsafe_stdlib` is its only toggle), so it was patched for
  the measurement and restored.
- **The 48 bytes** are `seal_load_mode` in `dlibs.c`: under text-only the
  core wraps the guest's `load` so the second door refuses bytecode as the
  first does, one C closure holding the real `load` as its upvalue. Absent
  in build13, present from build14. Both pins refuse `load(string.dump(f))`
  in a spawned child, verified by spawning one under each; nothing here is
  a security finding.
- **The 341 bytes** are `_DILUVIUM` in 0.15.1, a table every sealed guest
  carries. The core's own.
- **Why it passed before:** the checker's "exact" band was `max(1, 0.1%)`,
  92 B here, which absorbed the 48 from the build14 pin onward and only
  failed when the core's growth was added to it. Exact means exact now:
  integers to the integer, ratios to the C's four printed decimals, and a
  one-byte perturbation fails the gate.
- **Hypotheses eliminated on the way:** the version string in `_DILUVIUM`
  (both hosts print `5.5.1`; no effect), settling the workers four steps
  before measuring as the C does (no effect), DRT's `require` global (an
  artefact of the probe sitting beside other `.dlua` files, which the
  modules walker loaded), and the modules bootstrap (not generated for a
  module-less program).
- **Upstream asks, recorded here since this session cannot file them:**
  `swarm_bench` needs a way to open workers text-only so the baseline can
  be captured in DRT's configuration and the named term retired; and the
  amalgamated core built outside the Makefile's host target falls back to
  the Lua version for `DILUVIUM_BUILD`, so `_DILUVIUM.version` reads
  `5.5.1` under DRT and under `swarm_bench` alike, where the Makefile's
  own binaries say `0.15.1`.

**Issue #33: Nagle.** No TCP socket in the tree set `TCP_NODELAY`, so a
pair of small writes on any hop drt owned paid the far end's delayed ACK:
48 ms on loopback through a tunnel whose client had already set it, 200
ms on a Windows hop, and an RDP session through a parked leg felt it as
lag. Nine sites, one shape: the option goes on at every dial and every
accept. The tunnel's WebSocket client had no hook for it -- `connect_async`
dials inside itself -- so `connect` dials its own stream and hands it to
`client_async_tls_with_config`, the default connector when no roots are
supplied and the same rustls config as before when they are. Failure to
set the option is named where a call has an error path and swallowed in
the two std acceptors, where it is a latency cost rather than a refusal
and not one a supported target produces. Measured by two tests that
write one byte, wait five milliseconds, write another and time the
answer, median of nine: at the bridge and at the socket connector.
Upstream, ego-transport's own TCP dial (`platform/tcp_native.rs`) sets
nothing either, so an ssh session on the `ssh` connector still pays it
on its first hop; that is its issue to file.

**A credential as a header.** The tunnel's key lived only in the URL, so
it was in the request line of every proxy and access log between the two
ends. `drt tunnel --header 'Name: value'` and `tunnel.headers` put it on
the handshake instead; the dial that issue #33 made the tunnel's own is
where they go on, and `resolve` merges them per name, flag over file, and
refuses a malformed one or one beside a `listen` before anything is
dialed. The relay reads `Authorization: Bearer <key>` at the same door as
`?k=`, header first, with a disagreeing URL key refused. Measured: the
resolve merge and both refusals; and against a live relay, a caller and a
device each admitted by header alone, a wrong header refused with the
same 403, a right URL key beside a wrong header refused, and a `Basic`
scheme refused rather than fallen through.
CI #335 then failed the config corpus, which snapshots every corpus

tunnel blocks. Re-recorded, the diff being exactly those two lines --
and a reminder that the subset of tests run before that push was the

**Then the tunnel learned to say what it is doing.** The ask was plain:
"prints something when you run it so people know it's not broken". The
two listener modes already announced their bind; stdio mode said nothing
at all, a successful park said nothing, and every per-connection outcome
in the listen half, good or bad, returned without a word -- a caller
dropped for a reason the bridge kept to itself was indistinguishable from
a broken bridge. Three rules shaped the lines. State changes, not
heartbeats: "parked" once and again after a failure, never on the re-park
the relay's five-minute idle close brings. A person is told, a program
is not: the ProxyCommand form speaks only when stdin is a terminal,
because ssh relays that stderr to the terminal on every rsync and every
ProxyCommand tool is silent there. And no line shows a URL's query: the
device runs from a file so its `?k=` stays off `ps`, and a line that
echoed it would put it back, so the dial's errors drop it too. A
`shown(url)` helper is the whole of that rule.

## Step notes

- **1.** `Caller::Root | Caller::Node(u32)` in `drt-connector`; that enum
  *is* §2.3's two-valued scope. `Handles<R>` keyed by `(Caller, HandleId)`,
  generic over the resource, labelled by kind — no socket, no fd. Trait
  gained `call_as` and `release`, both defaulted; `route`/`dispatch` keep
  their signatures (11 connector test files call them) and delegate as
  `Root`; `route_as`/`dispatch_as` carry the caller. `PumpHost::released`
  drains the dispatcher and keeps the attributed report in `take_lost()`;
  `detached` never touches it. **Deferred to step 3:** draining
  `take_lost()` to stderr in the drive loop — `drt-swarm` has no stderr, and
  nothing real can be lost until a socket exists. `async-trait` added as a
  dev-dependency of `drt-swarm` for the pump test only.
- **2.** Step-1 adjustment, made here as §12 allows: `call_as` takes an
  `Asker { caller, grants }` — the scopes on every grant that permitted
  the call — because §4.3a's prefix scope is *per node* (on the grant),
  not per deployment (on the wiring), and the dispatcher was handing
  connectors only the wiring scope. Labels derive from a kept
  `k_label = HMAC(master, KDF_LABEL_DERIVE)` since the master is dropped;
  each label yields hmac and jwt subkeys under the existing labels
  (§4.2a). Table keyed `(Caller, label)` — same shape as `Handles`,
  name-addressed rather than handle-addressed. `release` reports nothing
  lost, as a claim: a label is derived, not stored. `jwt_sign {key}` is
  step 7; `do_jwt_sign` is untouched here. `Swarm::snapshot(id)` added
  (pub, read-only) for acceptance 15. `hmac`, `sha2` added as `drt`
  dev-dependencies so that test derives independently.
- **3 (verbs).** `connectors/socket` → `drt-connector-socket`, feature
  `connector-socket`, `full` only, wired in `cli.rs` like exec. Five
  verbs: `socket/listen {addr}`, `accept {handle}`, `read {handle, max?}`,
  `write {handle, data}`, `close {handle}`; no `connect` (§3.1, §10).
  `Handles<Socket>` keyed by `Asker.caller`; the caller-blind `call` is
  the root. **What waits, waits in the host:** `accept`/`read`/`write`
  return `Poll::Pending` on `WouldBlock` and the pump re-polls each step
  — the rest/ssh shape, no busy loop in the guest, no runtime needed.
  Scope `allow` is `ip:port` literals (port 0 = any port on that ip),
  checked at wiring. `release` closes everything the owner held and
  reports each connection whose peer was still there as
  `a connection with <peer>, cut`; a listener or an at-EOF connection is
  not a loss. `Swarm::host_mut` added; `DeployDriver::step` drains
  `take_lost()` to stderr as `drt: instance N lost <what>` (the step-1
  deferral, paid). Tests: 8 in the crate (fd count in its own binary —
  see facts), 1 in `crates/drt/tests/sockets.rs` through a real kill.
- **3 (transfer).** Built as CHECKPOINT A below says, after the owner's
  "please continue". `Handles::rekey(from, to, handle)` is the primitive
  (drt-connector, resource-agnostic, number unchanged). The connector keeps
  `offers: Vec<Offer {from, to, handle}>`, oldest first; `transfer` checks
  the caller holds the handle then records the offer (a second offer of
  the same handle replaces); `claim {handle}` is immediate, `claim {}`
  pends until an offer addressed to the caller exists, then re-keys and
  answers `{handle, peer}` (or `{handle, addr}` for a listener); `close`
  and `release` sweep offers in both roles. 9 connector tests
  (`tests/transfer.rs`); acceptance 6, 7, 14 in one deployment test: an
  acceptor root binds once, spawns a child per connection with only
  `claim/read/write/close`, transfers; each child claims `{}`, reads its
  subject, announces it on its exported outbox; one traps on `trap` and
  its loss is attributed to it while sibling and parent carry on; one
  serves to end-of-file and exits losing nothing.
- **4.** Resource-agnostic again: `Connector::ended() -> Vec<(Caller,
  String)>` (default empty) and `Dispatcher::ended()`; `Handles::take_where`
  is the sweep primitive; `SwarmHost::ended()` (default empty) is drained
  at the top of `Swarm::step`, before any wake, and each owner is
  `kill_subtree`'d where it lies with the parent told by the **`ended`**
  event — its own variant, detail = the connector's sentence.
  `PumpHost::ended` maps the dispatcher's `Caller::Node`s to instances.
  Socket side: `vital` on `listen`/`accept`/`claim` (claimant-side at
  claim, as CHECKPOINT A proposed — the flag is reset to the claimant's
  declaration on rekey); `ended()` = closes of vital handles by their
  owner + one non-blocking `peek` per vital connection per step; the
  entry leaves the table with the report. A vital listener ends only by
  its owner's close. 6 connector tests (`tests/vital.rs`); acceptance 11
  and 23 in one deployment test: the service is **hibernated** when the
  far end hangs up, is gone with no guest rebuilt, its second connection
  is cut and attributed, and the supervisor's `host.events` yields
  `ended <id>`.
- **5.** The same shape a third time: `Connector::notices() ->
  Vec<Notice {owner, queue, message}>` (default empty),
  `Dispatcher::notices()`, `SwarmHost::notices()` drained in `Swarm::step`
  after the vital sweep and before the wake loop, each a runtime push
  (`Sender::runtime(NodePath::root())`) into the owner's named queue; a
  push that fails — full, gone, cached without `wake_on_message` — is
  dropped as any such push is. `Handles::each` is the look. Socket side:
  `wake = true | "<queue>"` on `listen`/`accept`/`claim` (the claimant's
  own at claim, like `vital`); level-triggered and re-armed by the
  owner's own `read`/`accept`, so a queue never fills with one fact;
  message `{handle, ready = "read" | "accept"}`; a `wake` listener's sweep
  accepts up to `ACCEPT_SWEEP` (16) into a backlog the next `accept` hands
  out; end-of-file is said once and never again. 3 connector tests
  (`tests/wake.rs`); acceptance 4 and 13 in one deployment test: the
  service is hibernated, bytes wake it, it serves with the `inbox` handle
  and the socket handle it held before the park — twice, proving the
  re-arm — and `DILUVIUM_VERIFIED = 2c2f920d7fcf…` is asserted against
  `env!("DRT_DILUVIUM_REV")` so a pin bump fails the test until §3.5 is
  re-proved.
- **7 (worker).** `jwt_sign {claims, ttl?, key = <label>}`: header
  `{"alg":"HS256","typ":"JWT","kid":"<label>"}`, base64url unpadded, that
  member order every time, signed under the label's JWT subkey via a
  `label_jwt_key` sibling of `label_hmac_key`. Without `key`, byte-for-byte
  today's token. A `crypto.secrets` name is refused first, by name, saying
  the bytes are shared with a peer; an underived label refuses with hmac's
  "derived no label" sentence. `jwt_verify` decodes the header segment for
  `kid` only, looks the label up for **the caller**, rebuilds the header
  and compares bytes — `alg` is never read; unknown `kid` → `reason =
  "kid"`, header mismatch (two kids, reordered, `alg:none`) → `"alg"`, no
  kid → the constant header and default key behind `jwt = {
  accept_unkeyed = <bool> }` in the wiring scope (default true; off →
  `"unkeyed"`), unknown keys under `jwt` refused at wiring. One property
  statement in the module header changed to stay true: the MAC is checked
  before the *payload* is parsed; the `kid` is the one thing read ahead of
  it. `kid.rs` derives every hand-assembled token's key from the public KDF
  labels rather than asking the connector; acceptance 16's test asserts
  both that `hmac {key=L}` used the hmac subkey and that its MAC does not
  verify, with the JWT-subkey control verifying.
- **8 (worker, one fix by the main thread).** `DeployHost` no longer drops
  a park on `detached`; `released` drops it, so `next_deadline` spans
  hibernated instances and a woken instance resumes with the deadline it
  armed. `DeployHost::due(now)` lists parks past their deadline;
  `DeployDriver::step` wakes the hibernated ones **before** `sw.step()` —
  after it, `enforce_residency` would re-hibernate the woken instance
  undriven (stale `last_active`, first LRU pick): a wake loop. The floor
  is `residency.park_floor_ms` (default 30 000), `DeployHost::with_park_floor`,
  applied only when `config.residency` is `Some`; a timed park under it is
  refused at arm time as `Driven::Faulted` naming the timeout and the
  floor. **The fix:** the worker kept the whole `Park.wait` across a wake;
  queue handles are runtime identity, valid for one residency
  (`engine.rs`, `QueueHandle`), so a message-woken instance's readiness
  check ran against the old residency's handles and it sat parked forever
  — caught by acceptance 4's test on the merged tree. Now `Park.wait` is
  `Option<WaitSet>`: `attached` clears it, the deadline stays, and the next
  drive asks the restored instance for its wait again without re-arming.
- **9.** `crates/drt-plugin/src/tcp.rs`: `TcpChannel::dial(addr)`,
  `from_stream(TcpStream)` (the `spawn` row's dial-back, or a connection
  a node accepted), `peer()`; `impl Channel` with `ProcessChannel`'s
  answers (zero for not-now, `Closed` for a far end gone) over
  `std::net`, nodelay on. `cfg(any(unix, windows, target_os = "wasi"))`,
  the row's own targets. No frame changes, no delivery, no refusal moved
  (§8): two protocols over one `Channel`, never one. 6 tests against a
  loopback far side that is a thread speaking the crate's own codec.
  Nobody depends on `drt-plugin` yet; still not wired (§7.0).

## Facts learned (code over spec)

- A bare `*` is **not** a wildcard in the capability grammar:
  `drt_caps::implies` needs a character before the trailing star
  (`n > 1`). `"*"` is the literal name `*`. Patterns are `room:*`.
- A **global** is not in a snapshot: `_G` is a permanent (the header's
  `permanents` fingerprint) and its contents are never serialised. A
  parked coroutine's **locals** are, verbatim, as msgpack. §4.1's "the
  guest heap is the snapshot" means the stack-reachable heap. Any test
  that searches a snapshot for a guest value must keep it in a live local.
- The root instance already has `inbox` and `outbox`; a program uses
  `queue.lookup('inbox')`, never `declare`.
- The hostcall pump (`PumpHost`) is what `drt start` uses
  (`start.rs:715`), and a bare `sw.step()` loop completes hostcalls;
  `DeployDriver::step` adds only args delivery and residency.

- A `/proc/self/fd` count is **process-wide**: a test that counts it
  must be the only socket-opening test in its binary (cargo runs a test
  file's tests in parallel threads). `connectors/socket/tests/fds.rs` and
  `crates/drt/tests/sockets.rs` are each alone for that reason.
- An accepted `TcpStream` does not inherit the listener's non-blocking
  flag on every platform; it is set again after `accept`.
- `InstanceId` is `drt_swarm::InstanceId` (crate root), not `swarm::`.
- A parent learns its child's id from the `spawned` event on its
  `system/events` queue (`swarm.rs`, `do_spawn`): `{event = "spawned",
  id = <u32>}`. That number is the `Caller::Node(u32)` the connector sees.
- **There is no guest-to-guest delivery.** `host.spawn`'s own doc (the
  pinned diluvium's `types/guest.lua`): "A handle is NOT a channel: the
  swarm does not yet deliver endpoint references between instances, so
  there is no `child.push`." The guest API is `host.spawn{code, caps,
  budget, wake_on_message, sealed}` → `{id}`, `host.children()`,
  `host.events(waitms)`, `host.call/try`. Every instance has an exported
  `inbox` and `outbox` (dqueue.c 6.6). So acceptance 14's "joins its
  subject by message" is the child saying so on its exported outbox and
  the host reading it — the host is the deliverer of every cross-node
  message today (Peers.md §4), and the test asserts exactly that shape.
- `queue.wait` **returns the message**: `local h, msg = queue.wait({q})`
  pops it. A `queue.pop` after it gets nil. (Cost one fault to learn.)
- The readiness push wakes only an owner that hibernated **with
  `wake_on_message`** (spawn spec or hibernate op). A residency-policy
  hibernation of a node without it leaves the node unreachable to the
  push — §11 risk 4 lives exactly there. Not changed here; a service
  spawns with `wake_on_message = true`, and the connector doc says so.
- `host.events` passes an event name it does not know (`ended`) through
  as `{event, id, detail}`; the library does not filter variants.
- The guest's msgpack decoder reads `bin` and `str` into one string
  (dmsgpack.c), so a connector may answer bytes as `Binary`.
- `kill_subtree` → `release(index)` → `host.released` works against a
  cached slot (`inst == None`, `detached` already done at hibernation):
  acceptance 11's kill-while-hibernating needs no new swarm path, only a
  caller.
- The connector sees only `Asker.caller`. It **cannot** check that any
  other instance id is alive, is a descendant, or exists: parentage is the
  swarm's (`is_ancestor`), and neither the dispatcher nor the pump has a
  sight line to it. A transfer design that needs that check needs a new
  seam; the one below needs no check.

- (worker) `PumpHost` has `inner()` and no `inner_mut()`: a driver cannot
  mutate `DeployHost` outside the `SwarmHost` hooks; the deadline check is
  a read-only `due()` and every park mutation stays inside
  `drive`/`note`/`attached`/`released`.
- (worker) serde's wrong-type refusal under `deny_unknown_fields` does not
  name the field; only an unknown key's refusal names the key.
- (worker) The `faulted` event on `system/events` is `{event, id,
  detail}` — `detail`, not `reason`.

## CHECKPOINT A — the transfer verb (§3.2), proposed, not built

**Shape: offer and claim. Ownership is single-valued at every instant;
nothing is ever held under an instance that is not the one calling.**

```
socket/transfer {handle, to = <instance id>}      -> nil               (the holder)
socket/claim    {handle?}                         -> {handle, peer|addr} (the target)
```

**Who may call.** `transfer`: the current holder of `handle`, under
`host:socket/transfer`, naming any instance id in this root. No
descendancy check, for two reasons: the connector cannot make one (facts
above), and §3.2 says the ownership tree is not the membership graph —
who a node hands its connection to is the node's business, and the
recipient still has to be granted `host:socket/claim`. `claim`: any node
under `host:socket/claim`, and only for what was offered *to it* — the
offer is keyed by the dispatcher's `Caller`, never by anything in the
request. A per-connection child needs `claim/read/write/close` and
nothing else; the parent's cap set attenuates to exactly that.

**On the source side.** After `transfer`, the handle is **still the
holder's** until claimed: usable, closable (`close` withdraws the offer),
released with the holder if it dies first. A second `transfer` of the
same handle replaces the offer. At `claim` the entry is re-keyed from
`(holder, h)` to `(target, h)` — **same number**, since ids are unique per
table — and from then on the holder's every use of `h` is the constant
`no such handle`. A holder with a `read`/`write` in flight on `h` at that
moment gets `no such handle` on its next poll. Nothing is copied; the
descriptor never moves.

**`claim` with no handle waits.** The per-connection child cannot be
told its handle before it exists, and a retry loop in guest code is the
wrong fix. So `claim {}` is pending in the pump until the first offer
addressed to the caller lands — the same "what waits, waits in the host"
rule as `accept` — and answers with it. `claim {handle}` is immediate:
that offer or `no such handle`. The child's whole prologue is
`local c = host.socket.claim{}`.

**`vital` (§3.3, step 4)** goes on `claim {vital = true}`: the claimant
is the one whose lifetime is being tied, and the flag is a property of
the entry under its owner, so it is set where that entry is created.
Alternative if the acceptor should decide and the child not be able to
opt out: `transfer {handle, to, vital = true}`, carried through the
offer. Cheap either way; claimant-side is proposed.

**Error cases.**
- `transfer`: `handle` not the caller's → `no such handle`. `to` missing
  or not an integer → `args.to must be an instance id`. `to` is the
  caller → refused, `transfer to self`. `to` names an instance that does
  not exist or is dead → **not detectable here, and not a leak**: the
  offer sits under the holder until the holder closes it or dies, and
  the holder's release sweeps its offers.
- `claim {handle}`: not offered to the caller (offered to someone else,
  never offered, or the holder died first) → `no such handle`, one
  constant for all three, for §2.2's reason.
- `claim {}`: more than one offer addressed to the caller → takes the
  oldest; a child that is offered two connections was spawned by a parent
  that meant it to. (Alternative: refuse `more than one offer; name the
  handle`. Proposed: oldest.)
- `claim {}` with no offer ever coming: pends until the claimant dies —
  which, for a child whose parent died before offering, is the parent's
  `kill_subtree`. No timeout; §12's stop rule and this design agree.
- A dead claimant's pending offers: swept by `release(claimant)` too, so
  the offer map holds nothing for a dead node in either role.

**What it does not do.** Cross-root transfer (§10). Transfer as a
side-effect of spawn (§3.2: explicit verb). A liveness or descendancy
oracle: the one-phase alternative — `transfer` re-keys immediately and
the parent tells the child the number by queue — needs one, or leaks the
entry under a dead `to` until teardown; that is why two phases.

**Acceptance it unlocks:** 6 (accept → spawn → transfer → child serves
to completion), 14 (one acceptor per root, child joins its subject by
message), 7 (child traps mid-connection → its socket closes → siblings
and parent unaffected, through `release`).

## Windows stops being a reduced platform

The ask was "I don't want Windows to slip", and the answer turned out to
be one primitive rather than a strategy. `exec` opened with a
`compile_error!` calling itself unix-only, and the reason it gave was a
process group: the deadline has to kill everything the child started, not
just the child. That is one idea with two spellings, so the idea moved
into `drt_platform::process::Tree` -- a process group on unix, a Job
Object with kill-on-close on Windows -- and the connector lost its
refusal. Windows then built `full`, verified before any of this was
written down, so the `windows` profile that existed only to mean "`full`
minus `exec`" is deleted rather than redefined. A platform that needs its
own profile is behind; the honest way to record that it caught up is for
the profile to stop existing.

Earlier lines in this ledger that say `profile: windows` and
`clippy --features windows` are superseded by that and are left as they
were: they were true when written, and this section is where the change
is recorded.

Three things were stated rather than hidden. Windows has an assignment
window -- the job exists before the spawn but a process can only be
assigned after it exists, so a grandchild started in those microseconds
escapes; closing it needs `CREATE_SUSPENDED` and a thread handle
`std::process::Command` does not surrender, and the module header names
that as the change to make if it is ever observed. `argv` that is not
UTF-8 is refused by name on Windows rather than lossily converted,
because a replacement character in a path is a different path. And the
`spawn` transport puts its dial-back secret in the environment, not in
`argv` as `doc/Plugins.md` section 4.1 said: `/proc/<pid>/cmdline` is
world-readable and `/proc/<pid>/environ` is not, which is the same lesson
`drt tunnel` learned when its key moved out of the URL.

What is measured: the cross-build, and now `cargo test` on a Windows
runner, which nothing did before. What is not: nobody has watched a Job
Object sweep a tree on a real Windows box. The tests exist and CI will
run them, which is a different claim and is the one the matrix makes.

## Plugins: built, covered, and deliberately not shipped

`doc/Plan-0.7.0.md` §7.0 defers plugins on risk budget, and that holds.
What changed is that the deferral is now a *profile* decision rather than
an absence of code: the channel, the connector, the config key and the
capability menu are built and tested, and `plugins` is a cargo feature in
no named profile. `full` does not carry it, so the release artifact is
unchanged, which is what §7.0 asked for.

What landed, in order: the frame codec and session; the `process`,
`spawn` and `tcp` transports; `PluginConnector` behind the `Connector`
trait; scope-keyed routing, `(family, scope key)` to instance; the
`plugins` config block with eight refusals, all at load; and
`capabilities/list` reporting `kind` and `owner` from a connector's
`Backing`.

**Acceptance 8, 9 and 10 are covered**, which supersedes the "Not
covered: 8, 9, 10" line under *End of the release* — true when written,
recorded here per this ledger's convention. `node` scope gives each
caller its own process and releases it with its owner; `root` scope gives
every caller the same one and outlives any single node; a scope that is
neither is refused at load with both spellings in the message
(`crates/drt-plugin/tests/connector.rs`, `crates/drt-plugin/src/manifest.rs`).
Acceptance 12 remains slipped with datagrams.

**No `examples/` entry, on purpose.** The gate builds `--features full`
because that is the binary a user gets, so a plugins example would be
skipped on every CI run and unrunnable from a release download.
`examples/` is a declared human surface; a page there describing
something the shipped tool cannot do would be worse than no page. The
example is written the release `plugins` joins a profile, and not before.
`crates/drt-plugin/src/bin/plugin-echo.rs` is the fixture until then.

**Two things found while writing the tests, both fixed.** A relative
plugin `manifest` resolved against the working directory rather than the
config's, which `doc/Plugins.md` §3.1 says it must not and which is the
same bug `resolve_program` exists to prevent — a deployment would have
worked from its own directory and refused with "cannot be read" from
anywhere else. And two transport refusals, `tcp` everywhere and `process`
on Windows, fired at the first call rather than at load, contradicting
the rule every other refusal in the block follows.

**Still open:** §7's reply-ceiling question — telling a reply that cannot
fit from one that does not fit yet — which is a decision about what the
ceiling *is*, not code. Until it is answered a reply over
`MAX_FRAME_BYTES` ends the session by name, which is safe and blunter
than it should be.
