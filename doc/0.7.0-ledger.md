## 0.7.0-rc.2: the fidelity gate, and the 48 bytes

CI 319 refused the rc.2 cut on `density.resident_bytes_per_agent`: 92,210
against a baseline of 91,821. The trace, because every hypothesis on the
way was wrong and the record should say so:

| measurement | resident B / agent |
|---|---|
| committed baseline, C swarm on build13 (captured 2026-09-06) | 91,821 |
| C swarm on 0.15.1, stock | 92,162 |
| C swarm on 0.15.1, workers opened `DV_FLAG_TEXT_ONLY` | 92,210 |
| DRT on 0.15.1 | 92,210 |
| C swarm on build14, workers text-only | 91,869 |
| DRT on build14, current code | 91,869 |

- **DRT has no port drift.** In DRT's configuration the C swarm matches
  it to the byte on both cores. The C bench cannot set the text-only flag
  (`dvs_allow_unsafe_stdlib` is its only toggle), so it was patched for
  the measurement and restored.
- **The 48 bytes** are `seal_load_mode` in `dlibs.c`: under text-only the
  core wraps the guest's `load` so the second door refuses bytecode as the
  first does, one C closure holding the real `load` as its upvalue. Absent

  in a spawned child, verified by spawning one under each; nothing here is
  a security finding.
- **The 341 bytes** are `_DILUVIUM` in 0.15.1, a table every sealed guest
  carries. The core's own.
- **Why it passed before:** the checker's "exact" band was `max(1, 0.1%)`,
  92 B here, which absorbed the 48 from the build14 pin onward and only
  failed when the core's growth was added to it. Exact means exact now:
  integers to the integer, ratios to the C's four printed decimals, and a
  one-byte perturbation fails the gate.
- **Hypotheses eliminated on the way:** the version string in `_DILUVIUM`

## Facts learned (code over spec)

- A bare `*` is **not** a wildcard in the capability grammar:
  `drt_caps::implies` needs a character before the trailing star
  (`n > 1`). `"*"` is the literal name `*`. Patterns are `room:*`.
- A **global** is not in a snapshot: `_G` is a permanent (the header's
  `permanents` fingerprint) and its contents are never serialised. A
  parked coroutine's **locals** are, verbatim, as msgpack. §4.1's "the
  guest heap is the snapshot" means the stack-reachable heap. Any test
  that searches a snapshot for a guest value must keep it in a live local.
- The root instance already has `inbox` and `outbox`; a program uses
  `queue.lookup('inbox')`, never `declare`.
- The hostcall pump (`PumpHost`) is what `drt start` uses
  (`start.rs:715`), and a bare `sw.step()` loop completes hostcalls;
  `DeployDriver::step` adds only args delivery and residency.

- A `/proc/self/fd` count is **process-wide**: a test that counts it
  must be the only socket-opening test in its binary (cargo runs a test
  file's tests in parallel threads). `connectors/socket/tests/fds.rs` and
  `crates/drt/tests/sockets.rs` are each alone for that reason.
- An accepted `TcpStream` does not inherit the listener's non-blocking
  flag on every platform; it is set again after `accept`.
- `InstanceId` is `drt_swarm::InstanceId` (crate root), not `swarm::`.
- A parent learns its child's id from the `spawned` event on its
  `system/events` queue (`swarm.rs`, `do_spawn`): `{event = "spawned",
  id = <u32>}`. That number is the `Caller::Node(u32)` the connector sees.
- **There is no guest-to-guest delivery.** `host.spawn`'s own doc (the
  pinned diluvium's `types/guest.lua`): "A handle is NOT a channel: the
  swarm does not yet deliver endpoint references between instances, so
  there is no `child.push`." The guest API is `host.spawn{code, caps,
  budget, wake_on_message, sealed}` → `{id}`, `host.children()`,
  `host.events(waitms)`, `host.call/try`. Every instance has an exported
  `inbox` and `outbox` (dqueue.c 6.6). So acceptance 14's "joins its
  subject by message" is the child saying so on its exported outbox and
  the host reading it — the host is the deliverer of every cross-node
  message today (Peers.md §4), and the test asserts exactly that shape.
- `queue.wait` **returns the message**: `local h, msg = queue.wait({q})`
  pops it. A `queue.pop` after it gets nil. (Cost one fault to learn.)
- The readiness push wakes only an owner that hibernated **with
  `wake_on_message`** (spawn spec or hibernate op). A residency-policy
  hibernation of a node without it leaves the node unreachable to the
  push — §11 risk 4 lives exactly there. Not changed here; a service
  spawns with `wake_on_message = true`, and the connector doc says so.
- `host.events` passes an event name it does not know (`ended`) through
  as `{event, id, detail}`; the library does not filter variants.
- The guest's msgpack decoder reads `bin` and `str` into one string
  (dmsgpack.c), so a connector may answer bytes as `Binary`.
- `kill_subtree` → `release(index)` → `host.released` works against a
  cached slot (`inst == None`, `detached` already done at hibernation):
  acceptance 11's kill-while-hibernating needs no new swarm path, only a
  caller.
- The connector sees only `Asker.caller`. It **cannot** check that any
  other instance id is alive, is a descendant, or exists: parentage is the
  swarm's (`is_ancestor`), and neither the dispatcher nor the pump has a
  sight line to it. A transfer design that needs that check needs a new
  seam; the one below needs no check.

- (worker) `PumpHost` has `inner()` and no `inner_mut()`: a driver cannot
  mutate `DeployHost` outside the `SwarmHost` hooks; the deadline check is
  a read-only `due()` and every park mutation stays inside
  `drive`/`note`/`attached`/`released`.
- (worker) serde's wrong-type refusal under `deny_unknown_fields` does not
  name the field; only an unknown key's refusal names the key.
- (worker) The `faulted` event on `system/events` is `{event, id,
  detail}` — `detail`, not `reason`.

## CHECKPOINT A — the transfer verb (§3.2), proposed, not built

**Shape: offer and claim. Ownership is single-valued at every instant;
nothing is ever held under an instance that is not the one calling.**

```
socket/transfer {handle, to = <instance id>}      -> nil               (the holder)
socket/claim    {handle?}                         -> {handle, peer|addr} (the target)
```

**Who may call.** `transfer`: the current holder of `handle`, under
`host:socket/transfer`, naming any instance id in this root. No
descendancy check, for two reasons: the connector cannot make one (facts
above), and §3.2 says the ownership tree is not the membership graph —
who a node hands its connection to is the node's business, and the
recipient still has to be granted `host:socket/claim`. `claim`: any node
under `host:socket/claim`, and only for what was offered *to it* — the
offer is keyed by the dispatcher's `Caller`, never by anything in the
request. A per-connection child needs `claim/read/write/close` and
nothing else; the parent's cap set attenuates to exactly that.

**On the source side.** After `transfer`, the handle is **still the
holder's** until claimed: usable, closable (`close` withdraws the offer),
released with the holder if it dies first. A second `transfer` of the
same handle replaces the offer. At `claim` the entry is re-keyed from
`(holder, h)` to `(target, h)` — **same number**, since ids are unique per
table — and from then on the holder's every use of `h` is the constant
`no such handle`. A holder with a `read`/`write` in flight on `h` at that
moment gets `no such handle` on its next poll. Nothing is copied; the
descriptor never moves.

**`claim` with no handle waits.** The per-connection child cannot be
told its handle before it exists, and a retry loop in guest code is the
wrong fix. So `claim {}` is pending in the pump until the first offer
addressed to the caller lands — the same "what waits, waits in the host"
rule as `accept` — and answers with it. `claim {handle}` is immediate:
that offer or `no such handle`. The child's whole prologue is
`local c = host.socket.claim{}`.

**`vital` (§3.3, step 4)** goes on `claim {vital = true}`: the claimant
is the one whose lifetime is being tied, and the flag is a property of
the entry under its owner, so it is set where that entry is created.
Alternative if the acceptor should decide and the child not be able to
opt out: `transfer {handle, to, vital = true}`, carried through the
offer. Cheap either way; claimant-side is proposed.

**Error cases.**
- `transfer`: `handle` not the caller's → `no such handle`. `to` missing
  or not an integer → `args.to must be an instance id`. `to` is the
  caller → refused, `transfer to self`. `to` names an instance that does
  not exist or is dead → **not detectable here, and not a leak**: the
  offer sits under the holder until the holder closes it or dies, and
  the holder's release sweeps its offers.
- `claim {handle}`: not offered to the caller (offered to someone else,
  never offered, or the holder died first) → `no such handle`, one
  constant for all three, for §2.2's reason.
- `claim {}`: more than one offer addressed to the caller → takes the
  oldest; a child that is offered two connections was spawned by a parent
  that meant it to. (Alternative: refuse `more than one offer; name the
  handle`. Proposed: oldest.)
- `claim {}` with no offer ever coming: pends until the claimant dies —
  which, for a child whose parent died before offering, is the parent's
  `kill_subtree`. No timeout; §12's stop rule and this design agree.
- A dead claimant's pending offers: swept by `release(claimant)` too, so
  the offer map holds nothing for a dead node in either role.

**What it does not do.** Cross-root transfer (§10). Transfer as a
side-effect of spawn (§3.2: explicit verb). A liveness or descendancy
oracle: the one-phase alternative — `transfer` re-keys immediately and
the parent tells the child the number by queue — needs one, or leaks the
entry under a dead `to` until teardown; that is why two phases.

**Acceptance it unlocks:** 6 (accept → spawn → transfer → child serves
to completion), 14 (one acceptor per root, child joins its subject by
message), 7 (child traps mid-connection → its socket closes → siblings
and parent unaffected, through `release`).
